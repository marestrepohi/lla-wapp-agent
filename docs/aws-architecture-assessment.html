Un agente de cobranza en WhatsApp, con límites visibles

Lectura de la rama aws-deployment frente al assessment: qué existe en el demo, cómo trabaja el agente y qué falta para operar campañas de cobranza de forma gobernada.

Groq se conserva por la API disponible
Alcance del dibujoLa rama describe una demo AWS con datos sintéticos. Las líneas sólidas son componentes presentes en el código de esa rama; las punteadas son extensiones propuestas. Eso no certifica un despliegue productivo activo.

Qué debe responder la solución

El assessment pide priorizar WhatsApp para contactar suscriptores residenciales y comerciales con pagos vencidos, explicar datos y sistemas fuente, acciones y límites del agente, gobierno de campañas, fallas posibles y valor medible.

01 · Datos

Quién está vencido, cuánto debe, qué mensaje corresponde y de qué sistema sale cada dato.

02 · Agente

Razonamiento con herramientas, memoria acotada, acciones permitidas y escalamiento.

03 · Gobierno

Autorizar campañas, consentimiento, horarios, límites de contacto y pausa global.

04 · Resultado

Reducir mora y trabajo manual sin perder trazabilidad, control ni experiencia del cliente.

01 / Lo que implementa la rama

Entrada, procesamiento y respuesta

Webhook rápido y procesamiento asíncrono. La respuesta HTTP confirma que el mensaje se encoló; no confirma que el agente contestó ni que WhatsApp lo entregó.

Fuente actual

DynamoDB contiene registros sintéticos de clientes y cobranza para el demo. No se encontró conexión operativa a facturación, CRM, pagos ni una cola de atención humana.

Lo que acredita el código

La rama documenta el template SAM, validación/build/deploy y evidencia de un endpoint de demo. No acredita que la versión worker actual esté desplegada ni un recorrido extremo a extremo en producción.

Límite del modelo elegido

Groq es la API disponible que elegiste y queda en el diseño. Es inferencia fuera de AWS: los componentes de infraestructura sí son AWS, pero la solución no es estrictamente “100 % AWS” si ese requisito también incluye el proveedor del modelo.

02 / Dentro del agente

El modelo interpreta; las herramientas ponen límites

El LLM no debe decidir el saldo ni ejecutar operaciones financieras por texto libre. El grafo combina contexto conversacional con acciones deterministas y estado persistente.

03 / Para completar la propuesta

Gobernar campañas antes de ampliar el alcance

El assessment requiere conectores y controles que la rama no implementa. Se muestran como ampliaciones punteadas, sin presentarlas como componentes ya construidos.

04 / Riesgos y valor

Medir recuperación sin perder control

Primero acordar línea base y grupos de comparación. Una respuesta generada o un mensaje aceptado por Meta no equivalen a pago recuperado.

Saldo equivocado

Riesgo: la demo usa datos sintéticos. Control: leer saldo y estado desde facturación con frescura visible; no iniciar campañas si el dato está desactualizado o no concilia.

Mensaje indebido o alucinación

Riesgo: prometer condiciones o revelar datos. Control: acciones tipadas, plantilla aprobada, límites por intención, evaluación de conversaciones y escalamiento humano.

Duplicado / entrega incierta

Riesgo: reintentar tras un timeout puede duplicar el contacto. Control: idempotencia por wamid y campaña, callback de Meta, conciliación de SEND_UNKNOWN y cola de fallos.

Consentimiento / frecuencia

Riesgo: contacto fuera de regla o acoso por campañas repetidas. Control: elegibilidad auditable, opt-out efectivo, ventanas horarias, topes multicanal y botón de pausa global.

Dependencia de proveedor

Riesgo: indisponibilidad o cambio de política de Groq. Control: timeout, límites de reintento, degradación a atención humana, métricas de proveedor y revisión explícita del requisito AWS del assessment.

Seguridad y privacidad

Control: minimizar datos hacia el LLM, cifrar secretos y datos, IAM de mínimo privilegio, retención por propósito y auditoría de accesos y acciones.

Recuperación incremental

Monto y tasa pagados frente a grupo de control, por segmento y antigüedad.

Promesa cumplida

Conversión a promesa y pago dentro del plazo acordado.

Calidad del contacto

Entrega confirmada, respuesta, opt-out, queja y contacto por cuenta.

Operación y riesgo

Costo por recuperación, escalamiento humano, errores y saldo conciliado.

Lectura frente al “100 % AWS”: la rama usa AWS para API Gateway, Lambda, SQS, DynamoDB, CloudWatch, SNS, Secrets Manager y KMS. Groq (y Qdrant cuando se activa) son servicios externos. Se respeta la elección de Groq por disponibilidad de API; si el evaluador entiende “100 % AWS” como proveedor de inferencia incluido, esa brecha debe explicitarse en la presentación y validarse con quien evalúa. El assessment permite mocks para el prototipo y no exige un despliegue real en AWS.
